## Certification 8.7 — code intelligence at scale

### What the first measurement found

The harness was written for this row and the row failed twice before it passed, both times for
reasons worth keeping.

**1. The delta reindex read every file.** Noticing that nothing had changed cost a full read and
hash of the whole corpus, so the cost of a one-line change grew with the size of the repository
rather than with the change. Fixed by recording each file's size and last-write time next to its
digest and asking the filesystem first: see D-037.

| Corpus | Delta before | Delta after |
| --- | --- | --- |
| 2,000 files, nothing changed | 12.5 s | 0.6 s |
| 2,000 files, one changed | 8.2 s | 1.0 s |

**2. The first index buffered every parse result before writing one of them.** `pool.parse()` was
handed every path at once, so a 500,000-file corpus held 500,000 parse results in memory, reported
no progress at all, and would have lost the entire pass to any interruption — which contradicts the
"resumable if interrupted" half of certification 8.1. Fixed by parsing and persisting a bounded
number of files at a time.

A third defect surfaced with it: the set of files affected by a change was computed with a linear
scan inside a loop over every file, which is quadratic in the size of the repository. It is a set
lookup now.

**3. The first chunk size was wrong.** Parsing a thousand files at a time bounded memory but starved
the worker pool at every chunk boundary, and the first index went from 319 files/s to 94. Ten
thousand keeps every worker fed and still holds a bounded amount in memory: 272 files/s, within
noise of the unbounded version, with progress, resumability and a ceiling on memory that the fast
version never had.

| 20,000 files | First index | Delta, one file changed |
| --- | --- | --- |
| Before any of this | 62.6 s (319 files/s) | 2.4 s |
| Chunked at 1,000 | 213.2 s (94 files/s) | 3.6 s |
| Chunked at 10,000 | 73.5 s (272 files/s) | 2.7 s |

### Results

Run against plugin version 1.0.0, corpus generated by the harness above. The second run repeats the
first on the same machine and the same code — `src/intel/` has not been touched between them — so
the difference is the machine, not the indexer. It is recorded rather than replacing the first
because a number that halves for reasons nobody controls is a number to distrust in both directions.

The third column is the same corpus after the scan was changed to stat a chunk of files at a time
instead of one at a time. Measurement is what found it: the delta was assumed to be dominated by
edge resolution, and the pass now reports `scan`, `parse` and `edges` separately because it was not.

| | 500,000 files, 2026-08-20 | 500,000 files, 2026-08-22 | 500,000 on WSL, 2026-08-24 |
| --- | --- | --- |
| First index | 3,588.8 s (59.8 min), 139 files/s | 1,885.7 s (31.4 min), 265 files/s | 1,601.0 s (26.7 min), 312 files/s |
| Graph produced | 1,000,000 nodes, 500,000 edges | 1,000,000 nodes, 500,000 edges | 1,000,000 nodes, 500,000 edges |
| Delta reindex, one file changed | 306.8 s, 1 reparsed, 499,999 unchanged | 121.3 s, 1 reparsed, 499,999 unchanged | **38.9 s**, 1 reparsed, 499,999 unchanged |
| Peak memory across the pool | ~2.3 GB during parsing, ~1.3 GB steady | not sampled | not sampled |
| Where the delta went | not measured | not measured | scan 17.3 s · parse 0.0 s · edges 6.3 s |

**Verdict on the row.** The first index completes and is background work: it reports progress
throughout, persists as it goes, and an interruption costs the current chunk rather than the pass.
The delta reparses exactly the file that changed.

**What the delta actually spends five minutes on, and why it is recorded rather than hidden.** No
file is read that did not change — the stat cache sees to that — but two things still walk the whole
corpus:

1. The stat sweep itself: 500,000 `stat` calls, about 0.6 ms each on this machine with real-time
   antivirus in the path.
2. `affected()` and `resolveEdges()` each load the whole `index_state` table to answer "which files
   import a file that changed", and they load it separately, so the 500,000 rows are read and their
   reference lists JSON-parsed twice per delta.

Neither is proportional to the change, so "bounded" here means bounded parsing, not bounded work.
Two upgrades are identified and neither was taken during this phase:

- Loading the catalogue once and passing it to both callers halves the second cost. It is a small
  change, deliberately not made after the measurement rather than before it: a recorded number has
  to describe the code that produced it.
- A reverse-import index would make `affected()` proportional to the change instead of the corpus,
  and filesystem watching would do the same for the sweep. Both are subsystems, and D-005 already
  names the condition for taking that kind of remedy.

**Scale in context.** 500,000 files is the top of the supported range and roughly ten times a large
monorepo. At 20,000 files — a large project — the same code indexes in 73.5 s and deltas in 2.7 s.

## Certification — the matrix, executed

Run on 2026-08-21 against plugin version 1.0.0.

```
node tests-debug/certify.mjs
```

### What the first execution found

The matrix claimed 118 automated rows. Matching each row against a test that names it by number
found that **86 of them had nothing behind them**. Three different things were hiding under one
label:

| | Rows | What it was |
| --- | --- | --- |
| Tested, never labelled | 53 | the check existed; nothing tied it to the row it satisfied |
| Not tested at all | 26 | sections 1, 3, 6, 12 and 13 |
| Product missing, not just tests | 7 | see below |

The seven were not test gaps. Ten of the twenty-four commands in section 15 of the specification
did not exist; the user manual section 3.13 checks against did not exist; and two of the three
enforcement layers in section 5.2 — the `PreToolUse` hook and worktree reconciliation — had never
been built, so the separation of powers had one layer and claimed three.

### Defects the execution found in code that already shipped

| Where | What |
| --- | --- |
| `store/checkpoints.ts` | the signing key's Windows ACL was set with an asynchronous call nobody waited for, and the account name it passed was malformed. On this machine the key kept the temp directory's inherited ACL: eight principals, five with Modify |
| `workflow/machine.ts` | reporting a task the executor could not finish threw an invalid transition instead of consuming a repair cycle. Unreachable through the happy path, so no test had touched it |
| every git invocation | without `core.longpaths`, git on Windows cannot open a path past 260 characters. The index parsed nothing under one, and a candidate would have silently omitted every file there |
| `tests-debug/cycle-e2e.mjs` | the fixture plan authorized `src` while the executor also wrote the verification scripts it was told to run. Found by the reconciliation layer within a minute of it existing |

### WSL could not run at all until its runtime was replaced

The first attempt on WSL executed no rows. `Ubuntu-24.04` on this machine had **Node v18.19.1**, and
the plugin requires 22 or later: the store is built on `node:sqlite`, which does not exist before 22,
and the test suite runs TypeScript directly, which needs 22 as well. Confirmed rather than inferred
— the control plane was started under that Node and failed with `ERR_UNKNOWN_BUILTIN_MODULE`.

That is certification 12.9 answering in the negative before anything else could be asked: Windows on
26.3.0 and WSL on 18.19.1 are not the same runtime, so nothing measured on one would have described
the other.

Resolved with `tests-debug/wsl-node.sh`, which fetches the official distribution, verifies its
SHA-256 against the published `SHASUMS256.txt`, and unpacks it under `~/.local/node-<version>`. It
takes its version from the recorded Windows run rather than from a pinned minimum, so parity is the
default and not something to remember: a fresh machine that installed "22 or later" would pass every
other row and then fail 12.9.

No sudo, no package manager, and the distribution's own Node 18 left where it is. `rm -rf` on that
one directory undoes it. On this machine two lines were also added to `~/.profile` and `~/.bashrc`,
each marked `# added by Cycle certification: node for WSL`, so that `node` resolves to it in an
ordinary shell; the script itself never touches a profile.

All seven suites passed on both. The difference in the pass counts is only the rows each platform
does not have to answer: Windows skips the POSIX permission row and the mounted-worktree row; WSL
skips the long-path row, the case-insensitive scope row and the ACL row.

The WSL run is itself certification 12.7, because the source tree it certified sits on `/mnt/c`. The
harness says so rather than leaving it to be inferred, and checks what that arrangement could break:
the store opens, the index parses, a candidate freezes with exactly the changed file in it, and the
bytes on the mount are unchanged by any of it. Correct, and still slow enough to be discouraged.

**Effect on release.** Thirteen manual rows have no recorded result on either platform, and seven
automated rows describe a packaged artifact that Phase 15 has not built. Under the sign-off rule the
matrix is not green and Phase 14 does not close — but every row that can be executed today does
execute, on both platforms, and passes.
